# SecurityHandler generator

After updating the code generated by `ogen`, run this command from the project root:

```sh
go generate ./internal/security
```

The directive lives in `internal/security/generate.go`. The generator reads
`SecurityHandler` from `internal/ogen/api/oas_security_gen.go` and completely
replaces `internal/security/security.go` with a struct, a constructor, a
compile-time interface assertion, and all required methods. API key and Basic auth
methods have shared authentication and authorization implementations. Other schemes currently
contain `panic("<method name>: not implemented")`.

The existing constructor name, `NewPassthroughSecurityHandler`, is preserved for
compatibility with the application. Its dependencies and support types are
generated only for schemes present in the interface:

| Supported schemes present | Constructor arguments |
| --- | --- |
| None | No arguments |
| API key only | `apiKeys APIKeyStore` |
| Basic auth only | `basicAuth BasicAuthStore, passwords PasswordVerifier` |
| Both | `apiKeys APIKeyStore, basicAuth BasicAuthStore, passwords PasswordVerifier` |

Multiple methods using the same kind of authentication share these dependencies.
Their order is stable regardless of method order. For the current project schema:

```go
handler := security.NewPassthroughSecurityHandler(apiKeys, basicAuth, passwords)
```

Any manual changes to the output file are lost on the next generation run.

## API key support

API key methods are recognized by the credential argument's `APIKey string`
field, with an optional `Roles []string` field. Scheme and method names do not
need to contain `ApiKey`. The generator reads type declarations from the source
file and other active, non-test Go files in the same package, including ogen's
`oas_schemas_gen.go`. Local aliases and pointer arguments are supported.

The generated file declares the dependency interface:

```go
type APIKeyStore interface {
    LookupAPIKey(ctx context.Context, scheme string, hash [sha256.Size]byte) (APIKeyRecord, error)
}
```

Implement this interface using your database, configuration, or another trusted
key store, then pass it as the `apiKeys` constructor argument. The `scheme`
argument is the Go credential type name, such as `ApiKeyHeaderA3nKs`; it lets the
store keep credentials for different schemes separate. The store must find a
previously provisioned key in that namespace and return `ErrInvalidAPIKey` if it
does not exist. Implementations must be safe for concurrent requests.

`APIKeyRecord` contains:

- `Hash`: SHA-256 of the original key, produced by `sha256.Sum256([]byte(rawKey))`.
- `Subject`: the authenticated user or service identifier.
- `Roles`: the actual permissions granted to the key.
- `ExpiresAt`: expiration time; the zero value means no expiration.
- `Revoked`: whether the key has been revoked.

This contract is intended for randomly generated, high-entropy API keys, not
human passwords. Raw keys are not sent to the store. The generated implementation
rejects empty keys, compares fixed-length hashes with
`crypto/subtle.ConstantTimeCompare`, checks revocation and expiration, and requires
every role from the credential's `Roles` field to be present in the stored record.
The credential's roles are operation requirements supplied by ogen, not proof
that the caller has those roles.

Successful authentication adds an `APIKeyIdentity` to the returned context.
Use `APIKeyIdentityFromContext(ctx, scheme)` to retrieve its `Subject` and `Roles`.
Identities for different schemes coexist, so AND requirements preserve all
authenticated identities. Role slices are copied to avoid mutating shared data.

Errors can be inspected with `errors.Is`:

- `ErrInvalidAPIKey`: empty, unknown, mismatched, revoked, or expired key.
- `ErrAPIKeyForbidden`: the key lacks one or more required roles.
- `ErrAPIKeyStoreNotConfigured`: the constructor received a nil store.

Store errors are wrapped while preserving their identity. Canceled contexts are
rejected before accessing the store. A nil store always rejects API key requests;
the application currently passes nil until a real store is configured.

## Basic auth support

Basic auth methods are recognized by the credential argument's `Username string`
and `Password string` fields, with an optional `Roles []string` field. Detection
does not depend on method or scheme names. Local aliases and pointer arguments
are supported, as with API keys. Ogen already extracts the username and password
from the HTTP request; the generated handler authenticates these credentials.

The generated file declares two dependency interfaces:

```go
type BasicAuthStore interface {
    LookupBasicAuth(ctx context.Context, scheme, username string) (BasicAuthRecord, error)
}

type PasswordVerifier interface {
    VerifyPassword(ctx context.Context, passwordHash, password string) (bool, error)
}
```

The store finds a user within the credential type's namespace and returns
`ErrInvalidBasicAuth` for unknown users. It receives no plaintext password.
`BasicAuthRecord` contains:

- `PasswordHash`: an encoded hash, including its algorithm, salt, and cost parameters.
- `Subject`: the authenticated user identifier.
- `Roles`: the actual permissions granted to the user.
- `Disabled`: whether the account is disabled.
- `ExpiresAt`: expiration time; the zero value means no expiration.

The verifier checks a password against the stored hash. Implement it using the
password hashing library and encoding already used by your application, for
example an adapter around `golang.org/x/crypto/bcrypt.CompareHashAndPassword`.
No password hashing algorithm or third-party dependency is hardcoded into the
generated code. Return `(true, nil)` for a match, `(false, nil)` for a mismatch,
and an error for operational failures or invalid hash encodings.

For an unknown user, the handler still invokes the verifier with an empty hash.
The verifier must perform a dummy verification with the same cost as a normal
check and then return `(false, nil)`, to reduce timing differences that could
reveal existing usernames. The handler always rejects empty hashes, even if the
verifier returns true. Both dependencies must be safe for concurrent requests;
neither should log plaintext passwords or include them in errors.

The generated implementation rejects empty usernames and passwords, checks the
verification result, account status and expiration, and requires every role
supplied by ogen. `operationName` is not a scheme identifier: it is intentionally
ignored, while credential roles contain the operation's role requirements.

On success, `BasicAuthIdentityFromContext(ctx, scheme)` returns a verified
`BasicAuthIdentity` with `Subject`, `Username`, and copied `Roles`. Passwords and
hashes are not added to the context. Identities for different Basic auth schemes
and API key identities coexist.

Errors can be inspected with `errors.Is`:

- `ErrInvalidBasicAuth`: empty or incorrect credentials, unknown user, empty hash,
  or disabled/expired account.
- `ErrBasicAuthForbidden`: the user lacks one or more required roles.
- `ErrBasicAuthStoreNotConfigured`: the constructor received a nil store.
- `ErrPasswordVerifierNotConfigured`: the constructor received a nil verifier.

Store and verifier errors are wrapped while preserving their identity. Context
cancellation is checked before and after dependency calls. The application
currently passes nil dependencies, so Basic auth requests are rejected until
real implementations are configured. Use HTTPS and request rate limiting in the
HTTP/deployment layer; these are outside the generated handler's scope.

## Configuration

Configure the generator directly in the `//go:generate` directive:

- `-source`: Go file declaring the interface.
- `-output`: destination file; missing directories are created automatically.
- `-api-import`: import path of the package containing the interface and API types.
- `-package`: destination package name (default: `security`).
- `-type`: struct name (default: `passthroughSecurityHandler`).
- `-constructor`: constructor name (default: `NewPassthroughSecurityHandler`).

The first three flags are required. Relative paths in the directive are resolved
from `internal/security`, the directory containing `generate.go`.

You can also invoke the generator directly from the project root:

```sh
go run ./cmd/securitygen/main.go -source internal/ogen/api/oas_security_gen.go -output internal/security/security.go -api-import ogen-sec/internal/ogen/api
```

The implementation and its tests live in `internal/securitygen`. Its exported
`Run(args []string) error` function parses the flags and generates the output.
`cmd/securitygen/main.go` calls this function and handles errors and the process
exit status.

The generator uses only the Go standard library. It does not run `ogen` or
require the API package to compile first. It supports interfaces with directly
declared exported methods, as emitted by `ogen`. Embedded interfaces and dot
imports are rejected before the output is overwritten.

## Tests

```sh
go test -v -cover ./internal/securitygen
```

The tests cover type detection, conditional constructor dependencies, renamed
schemes, aliases, signature preservation, and generation failures. They also
generate temporary modules and execute tests against the generated handlers,
covering header, query, and cookie API keys, Basic auth password verification,
unknown users, disabled accounts, role requirements, expiration, revocation,
dependency errors, cancellation, and identity propagation across schemes. The
temporary modules use only standard-library dependencies and disable network
downloads.
